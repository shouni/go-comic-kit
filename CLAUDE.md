# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

go-comic-kit is a Go library for AI manga/comic generation with character-identity consistency. It is the successor to [go-manga-kit](https://github.com/shouni/go-manga-kit) (now frozen, kept only for the ap-manga-web showcase) and is the core library for **ap-comic**, an MCP-enabled orchestrator service.

**README.md is the entry point** (overview, project layout, quick start, doc index); the reference material lives in `docs/` — `schema.md` (MangaState and its invariants), `configuration.md` (Config and prompt DI), `operations.md` (the operation set and error classification), `assets.md` (artifact paths). Read the relevant page before making non-trivial changes, and keep it in sync when changing a contract.

## Common commands

```bash
go build ./...
go test ./...
go test ./internal/operations/ -run TestGenerateChapterScript -v   # single test
go test -race ./...                                    # CI runs with -race
go vet ./...
gofmt -l .
golangci-lint run    # config in .golangci.yml (v2 format; errcheck, staticcheck, gocritic, revive, ...)
```

CI (`.github/workflows/ci.yml`) runs exactly: `go build`, `go vet`, gofmt check, `go test -race`, golangci-lint, and govulncheck. revive requires doc comments on all exported symbols (this repo's comments are written in Japanese).

Dependencies (`gemini-image-kit`, `go-character-kit`, `go-remote-io`, `go-utils`) are pinned to the versions proven in go-manga-kit — don't bump casually. `go-gemini-client` is at v1.15.1+ on purpose: script generation relies on its `GenerateOptions.ResponseJSONSchema` (structured output / constrained decoding, same approach as its `lyria` package) so the model's JSON is grammar-constrained instead of regex-repaired.

**Nothing in this repo imports `google.golang.org/genai`.** The SDK stays inside `go-gemini-client`: `operations.StructuredGenerator` is an alias of `gemini.Generator` (prompt + attachments, no `genai.Part`), schemas in `internal/operations/schemas.go` are plain `map[string]any` JSON Schema, safety thresholds come from `gemini.SafetyBlockNone`, and the image core takes `gemini.Model`. Re-introducing `genai.Schema` or `GenerateWithParts` would pull the SDK back into this kit's signatures and into every mock that implements them. `internal/operations/json_response.go`'s `parseJSONResponse` calls `gemini.CleanJSONResponse` (go-gemini-client) as a defensive layer against trailing noise the model still occasionally emits despite constrained decoding.

## Architecture

### Core principle: MangaState + idempotent operations

`ports.MangaState` (persisted as `comic_state.json`) is the single source of truth for one work: chapters, panels, design-sheet records, page artifacts, and the generation conditions (`GenerationRecord`: seed/prompt/model) of every image. All operations are idempotent and state-in/state-out:

| Operation (ports interface) | Status |
|---|---|
| `OutlineGenerator.GenerateOutline` — source text → chapters-only state | implemented (`internal/operations/outline.go`) |
| `ChapterScriptGenerator.GenerateChapterScript` — panels for ONE chapter, replaces existing | implemented (`internal/operations/chapter.go`) |
| `DesignSheetGenerator.GenerateDesignSheet` — identity-anchor sheets | implemented (`internal/operations/design.go`) |
| `PanelImageGenerator.GeneratePanel` — per-panel image gen/regen (seed re-roll or `EditPrompt` image-to-image edit) | implemented (`internal/operations/panel.go`) |
| `PageImageComposer.ComposePage` — compose one page from its panels (layout map, balloons, `EditPrompt` edit) | implemented (`internal/operations/page.go`) |
| `PanelImageGenerator.GenerateAllPanels` / `PageImageComposer.ComposeAllPages` — batch generation at `Config.MaxConcurrency` | implemented (same runners, same interfaces as the single-item methods; `internal/operations/batch.go` holds the shared `runBatch`) |

Batch operations return the state **and** a joined error on partial failure — the successes are already recorded, so the caller saves the state and re-runs with `BatchOptions{SkipGenerated: true}` to retry only what failed. Because they run panels/pages in parallel, `PanelResourceProvider` / `PageResourceProvider` implementations must be safe for concurrent use, and the per-item render (`renderPanel` / `renderPage`) must not write to shared state — it returns a record that the caller applies after `Wait`.

There is deliberately NO publish/export operation (v1's HTML/Markdown output was dropped): presentation is the consuming app's job, reading the state document and GCS images directly.

Script generation is deliberately **two-stage** (outline → per-chapter panels) to keep each LLM call's JSON schema small and to give chapter-level regeneration granularity. Downstream regeneration (`regenerate_panel` etc.) works by re-running the same operation against the state.

### Error classification

Operations wrap their errors with the sentinels in `ports/errors.go` (`ErrNotFound`, `ErrInvalidRequest`, `ErrGeneration`) so the consuming app maps them to HTTP status with `errors.Is` instead of matching message strings. New failure paths must pick one of the three — an unwrapped `fmt.Errorf` is invisible to the caller's classification. (`ErrConfigInvalid` is the fourth sentinel but is not an operation error: `Config.Validate` returns it from `workflow.New` at construction time, never mid-request.) The image pipeline's non-AI failures were the hole this rule was written for: saving an image and building its path used to return bare errors. `renderImage` now classifies them — path building fails on the caller's arguments (`OutputDir`, page number) so it is `ErrInvalidRequest`; the storage write is usually transient so it is `ErrGeneration`.

### Data-model invariants

- **Every image generation is seeded.** `resolveSeedChain` draws a seed when nothing else supplies one, because the API picks its own seed otherwise and never reports it back: `GenerationRecord.UsedSeed` would stay 0, the chain's "reuse the previous seed" step can't distinguish that from unset, and a work whose seeds are never specified could never be regenerated identically. Seeds are bounded to int32 because go-gemini-client rejects anything wider.
- **IDs are assigned server-side, never trusted from AI output**: chapters get `ch01`-style IDs, panels get `ch01-p03`-style IDs. These are regeneration targets and must stay stable.
- A `Panel` holds `Characters []PanelCharacter` (who appears — independent of who speaks) and `Dialogues []DialogueLine` (multiple balloons; empty `SpeakerID` = narration). Character relationships are free text in `PanelCharacter.Action`.
- `Prominence` controls reference-image attachment: `primary`/`secondary` characters get their design sheets attached at image-gen time; `background` (mobs) get none. `ReferencedCharacterIDs()` / `UniqueReferencedCharacterIDs()` encode this rule.
- Character IDs unknown to characters.json are **demoted to background** during chapter-script normalization — otherwise reference resolution silently falls back to the default character and draws the wrong person.
- Dialogue `SpeakerID`s unknown to characters.json are converted to narration (empty speaker + `narration` kind) during normalization — same "never trust AI-supplied IDs" rule as `CharacterID`; otherwise the raw ID gets drawn where the speaker's name belongs.
- `primary` + `secondary` per panel is capped at `ports.MaxReferencedCharactersPerPanel` (3); the overflow is demoted to `background`, keeping primaries and preserving in-panel order. The README documented this limit long before the code enforced it.
- After changing a chapter's panels, call `state.ReplaceChapterPanels` (keeps chapter order, updates `Chapter.PanelIDs`) then `state.Repaginate`. `Repaginate` breaks pages at chapter boundaries (never mixes two chapters onto one page) and drops `PageArtifact`s whose panel composition changed, so stale page images can't survive a chapter regeneration. Artifacts whose composition is unchanged are kept, so regenerating one chapter doesn't force re-composing unrelated pages.

### Packages

Public API surface is deliberately small: `comic`, `ports`, `asset`, `store`, `workflow`. Everything else lives under `internal/` because go-comic-kit currently has exactly one consumer (`ap-story`), which only ever imports those five — there's no reason to expose implementation packages nobody outside this module touches. If a second consumer ever needs direct access to `internal/operations` or `internal/layout`, un-hiding a package is a one-line move; keeping them internal until then costs nothing.

- **`comic`** — the MangaState data model and its methods (chapters, panels, dialogue, design-sheet records, page artifacts, `Repaginate`). Depends on nothing in this module; everything else imports it. Split out of `ports` because a package named for its contracts should not also be the place the data model lives — the same `domain`/`ports` split the sibling apps use. It is `comic` rather than `domain` because this one is a public package name that consuming apps import alongside their own `internal/domain`.
- **`ports`** — the operation contracts (interfaces), their request/option types, and `Config`. Imports `comic`; nothing here holds data of its own.
- **The kit ships no prompts at all.** All five (`OutlinePrompt`, `ChapterScriptPrompt`, `DesignSheetPrompt`, `PanelPrompt`, `PagePrompt`) are required in `workflow.Args` and `validateArgs` rejects a nil one. It used to embed terse defaults; the only consumer (ap-story) implemented all five anyway, so the defaults were a fallback nobody reached that still had to be maintained and tested. Prompt text is iterated on per work, exactly like style suffixes and model names, and none of those should need a kit release to change. Earlier prompt bodies are in git history if a new consumer wants a starting point. The outline/chapter mode used is persisted in `MangaState.ScriptMode` so regeneration uses the same prompt.
- **Prompt assembly never lives in an operation.** The runners決めるのは「どの画像を何番目に添付したか」だけで、本文は `ports.PanelPrompt` / `ports.PagePrompt` の実装が組み立てます。`PanelPromptData.SubjectIDs` と `PagePromptData.CharacterFile` / `PanelFile` がその番号の唯一の情報源で、ここがずれるとモデルは別人の参照画像を見ながら描きます。`promptSet` (`prompt_set.go`) が system/user/negative を組で持ち回り、`GenerateOptions.PromptOverride` は user だけを置き換えます。
- **`internal/operations`** — one file per operation (`outline.go`, `chapter.go`, `design.go`, `panel.go`, `page.go`), plus purpose-named shared helpers (`gen_opts.go`, `json_response.go`, `source_text.go`, `character_roster.go`, `image_output.go`, `seed.go`, `prompt_set.go`, `batch.go`, `schemas.go` — no grab-bag `common.go`). `image_output.go`'s `renderImage` owns the generate → save → `GenerationRecord` tail shared by panels, pages and design sheets; the three operations keep only what differs (prompt assembly, where the file goes, the log line). Operations (`OutlineRunner`, `ChapterScriptRunner`, etc. — the `Runner` suffix stays on the types even though the package is `operations`) depend on narrow interfaces (`ImageGenerator`, `StructuredGenerator`), not concrete layout types, so tests use lightweight fakes. `ImageGenerator` is one method (`Generate`) since gemini-image-kit v1.13 merged single and fused generation — the reference count is now just `len(ImageRequest.Images)`, so there is nothing left for a separate "fusion" interface to mean. Building an image request is pure: each runner's `buildRequest` takes neither a context nor the state, because collecting references no longer performs I/O.
- **`internal/layout`** — aspect-ratio constants and normalization (`types.go`). Panels and pages are both **3:4**, and `designAspectRatios` includes "3:4" for exactly that reason: `char.ReferenceURLFor(aspectRatio)` falls back to the aspect-agnostic `ReferenceURL` when no entry matches, so a design sheet that cannot be generated at the panel's ratio silently disables the drift suppression that aspect-matched references exist for. Adding a new panel/page ratio means adding it here too. It used to also hold `ComicComposer`, which pre-uploaded reference images to the File API and cached the resulting URIs behind double-checked locking + singleflight. gemini-image-kit v1.12.2 moved that decision into `ports.ReferenceResolver` (`GeminiImageCore.ResolveReference`: Vertex + `gs://` passes through, Gemini API uploads once via a singleflighted, cached `EnsureUploaded`), so the operations now pass `ImageURI{ReferenceURL: url}` and the kit resolves it. Do not reintroduce a pre-upload pass here — it would duplicate the kit's cache and re-open the drift that had this copy and go-veo-orchestrator's diverge.
- **`asset`** — the single place that knows where artifacts live. Exposes purpose-named builders (`StatePath`, `PanelImagePath`, `PageImagePath`, `DesignSheetPath`, `CharacterDesignPrefix`) rather than re-exporting `go-utils/urlpath`; `go-utils` is an implementation detail confined here. Layout rules that used to be smeared across `design.go` / `panel.go` / `page.go` / `store.go` (and re-derived by ap-comic via `fmt.Sprintf`) now live here, including `DesignFileTag`'s rune-boundary truncation and `SanitizeFileName`. When adding an artifact kind, add its path function here — do not `path.Join` in an operation.
- **`store`** — Load/Save of the MangaState document (`comic_state.json`, upsert-style overwrite; Load rejects newer schema versions).
- **`workflow`** — the DI layer: `workflow.New(Args)` assembles all operations from **one** image generation unit — design sheets, panels and pages all use `Config.ImageModel`. There used to be a standard/quality split (flash for panels, pro for sheets and pages) plus an optional second client (`Args.AIClientQuality`); which model counts as "quality" is Google's lineup talking, not a distinction this kit can own, so the consuming app now picks one model and offers alternatives in its own UI if it wants them. It calls `Config.ApplyDefaults` then `Config.Validate`: the two model names and the two style suffixes are **required** and have no kit defaults, because model IDs rot on Google's release schedule and style suffixes are per-work art direction — both must be changeable without a kit release (the same reason prompt bodies are DI'd out to the app). Everything else — concurrency, timeouts, chapter/panel limits — keeps its default here, since those encode how to run this kit without breaking it and a zero value there fails silently rather than loudly. `AspectRatio`, `PanelImageSize` and `PageImageSize` default too (3:4, 1K, 2K — the values that used to be hardcoded in `internal/layout`), but an *unknown* value is rejected by `Validate` rather than normalised away, because silently ignoring a requested ratio is the failure nobody notices. **One ratio covers panels, pages and design sheets on purpose**: a sheet generated at a ratio the panels never use falls back to the aspect-agnostic `ReferenceURL`, which silently disables the drift suppression that aspect-matched references exist for. `DesignSheetRequest.AspectRatio` still overrides it per call, for sheets meant to be consumed elsewhere. All five prompts come from `Args` and are required; `GenerateOptions.PromptOverride` still allows a per-call override of the user body. Call `Operations.Close() error` when done to stop the internal TTL caches; it is `sync.Once`-guarded and nil-safe, and the cleanup func is private (registered via `SetCloseFunc`) so a caller cannot swap it out. This mirrors `go-veo-orchestrator`'s `Workflows` — the sibling kit at the same layer, with the same dependency set. `Config.RequestTimeout` reaches reference uploads as `GeminiImageCoreConfig.UploadTimeout` (it used to be passed to `layout.NewComicComposer`). All AI calls (text + image) are wrapped in **singleflight decorators** (`workflow/singleflight.go`): identical in-flight requests are collapsed to one API call, shared responses are cloned per caller, and the shared execution runs on a detached context so one caller's cancel can't kill piggybacking callers. This only dedupes within one process — durable idempotency is the job of the consuming app via `GenerationRecord`. The same decorators carry a `callGuard` that makes two previously-dead `Config` fields real: `RateInterval` (minimum spacing between AI calls, one limiter shared by text + image because quota is per project) and `RequestTimeout` (per-call cap, replacing the old hardcoded 5-minute constant; also passed to `layout.NewComicComposer` for reference uploads). The rate-limit wait happens *outside* the timeout so a busy queue can't manufacture timeouts. Note that throughput is bounded by `1/RateInterval` regardless of `MaxConcurrency` — setting both high-interval and high-concurrency is contradictory.

### Prompt-quality rules (hard-won, do not regress)

- **`Config` holds no art direction at all.** Every style word travels per call as `StyleMode` (`GenerateOptions`, `BatchOptions`, `DesignSheetRequest`) and is resolved by the injected prompt implementation, which is also the only place that holds the negative prompt belonging with it. Design sheets take their *own* mode resolution: panel/page art direction may use cinematic lighting, but sheets must NOT — they are identity anchors and baked-in lighting contaminates every downstream generation, so an implementation must map a mode to a sheet-safe suffix rather than reusing the panel one. `internal/operations/design.go` additionally force-appends flat-lighting/white-background/five-fingers constraints after any suffix and sets a system prompt + negative prompt (finger anatomy, text/label/swatch exclusion).
- Design-sheet filenames from many/long character IDs are truncated at rune boundaries with a CRC32 suffix (`designFileTag`) to respect filesystem name limits without collisions.
- Per-call art direction travels as a **name, not resolved text**: `GenerateOptions.StyleMode` / `BatchOptions.StyleMode` pass straight through to `PanelPromptData.StyleMode` / `PagePromptData.StyleMode`. A style is a pair — the suffix and the negative prompt that belongs with it (a monochrome style needs `monochrome` *out* of the negative and `color` *in* it) — and only the prompt implementation holds both halves. Resolving the suffix here would leave the negative prompt behind and let the two contradict each other.

### API shape rules

- **Batch scopes to a chapter through `BatchOptions.ChapterID`, not through new methods.** Script generation has a chapter unit and image generation did not, which meant the expensive half of the pipeline could only be run all-or-nothing. One field on the existing options covers panels and pages symmetrically and composes with `SkipGenerated`. Pages can be filtered by chapter only because `Repaginate` never puts two chapters on one page — if that invariant goes, chapter-scoped recomposition starts pulling in the neighbouring chapter's pages. An unknown chapter ID is `ErrNotFound`; treating it as a zero-target success hides a typo as "ran, did nothing".
- **Batch is a method on the single-item interface, not a separate one.** `PanelImageGenerator` carries both `GeneratePanel` and `GenerateAllPanels`; `PageImageComposer` likewise. They were separate interfaces with separate `Operations` fields (`PanelBatch` / `PageBatch`) that pointed at the *same* runner, so the struct had seven fields for five capabilities and every reader had to discover that two pairs were aliases.
- **Every seed is `*int64`.** `GenerateOptions`, `BatchOptions` and `DesignSheetRequest` all use nil for "resolve it for me". `DesignSheetRequest.Seed` used to be a bare `int64` where 0 meant the same thing, which is exactly the kind of near-miss that makes an API feel arbitrary. If you add an option struct, follow the pointer.
